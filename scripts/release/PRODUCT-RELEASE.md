# 세 저장소의 공개 제품 기준

`product-release.json`은 **이미 공개된 앱**과 **공식 발표자료**를 연결하는 기준이다. Web의 패키지 버전과 발표자료 편집 차수까지 앱 버전으로 덮어쓰지 않는다.

- 원본: 본체 `scripts/release/product-release.json`
- Website 사본: `DAOU.Athena-Web/config/product-release.json`
- 발표자료 사본: `DAOU.Athena-Presentation/release/product-release.json`

세 파일은 바이트 단위로 같아야 한다. 앱의 공개 버전·태그·소스 커밋·설치 파일 해시, 모의투자/모델/그래프의 지원 범위, 공식 PPTX/PDF/대본/가이드의 해시를 함께 고정한다. Website는 빌드 시 이 사본을 읽는다. 브라우저에서 `releases/latest`를 조회해 링크만 바꾸지 않는다.

## 현재 공개본과 개발 소스

현재 공개 앱은 v0.1.6이며 원본 소스는 `4188d70aec2b45cf095e7d71b6e587358559d91a`이다. 이후 main의 검증 도구와 공개 메타데이터 수정은 해당 설치 파일에 포함되지 않는다. 앱 버전 문자열이 같아도 소스 커밋이 다르면 검사는 `unreleased-source`로 표시한다.

수정된 앱을 배포할 때는 기존 `set-version.mjs`로 새 버전을 정하고 해당 태그에서 설치 파일을 만든다. v0.1.5의 기존 바이너리를 같은 이름의 다른 내용으로 바꾸지 않는다. 새 설치 파일·build-info·검증이 준비된 다음 이 기준표를 갱신한다.

발표자료는 사용자 결정에 따라 수정된 **39장본**이 공식 기준이다. 원래의 43장·55장 자료와 이관 명세는 과거 버전으로 보존한다. 발표를 바꾸면 반드시 다시 출력하고 PPTX뿐 아니라 PDF·대본·진행 가이드·Website 미리보기의 출처 해시도 바꾼다.

## 배포 후보 검사

세 저장소가 형제 폴더에 있을 때:

```powershell
python scripts/release/check-product-release.py --online --receipt .omc/artifacts/product-release-verification.json
```

다른 위치는 `--web-root`와 `--presentation-root`로 지정한다. `--online`은 GitHub CLI 인증을 사용해 정식 릴리스 자산의 digest 및 실제 build-info의 버전/원본 커밋·LAYA 모델/배포 명세 해시를 대조한다. 로컬 정책 파일 해시는 배포 명세의 `policy_sha256`와 같아야 한다. 자격증명은 기록하지 않는다.

온라인 검사는 각 저장소의 현재 원격 `main`도 직접 읽는다. 현재 HEAD가 그 커밋을 포함하지 않으면 실패하므로, 오래된 원격 추적 정보만으로 최신이라고 판정하지 않는다. 먼저 로컬 작업을 보존하고 원격 변경을 가져와 통합한 뒤 다시 검사한다. 검사는 파일 이동·stash·merge·push를 자동 실행하지 않는다.

공개 앱은 GitHub가 최신 정식 릴리스로 지정한 태그와도 같아야 한다. 새 정식 릴리스가 나왔는데 세 기준표가 모두 과거 버전을 가리키는 경우에도 실패한다. 웹 브라우저의 링크를 자동 변경하지 않고, 새 산출물과 기준표를 함께 검증해 다음 배포에 반영한다.

PASS의 범위는 로컬 파일과 기준표의 일치다. 세 저장소의 HEAD와 미커밋 상태도 영수증에 남긴다. 미추적 파일이 있는 상태에서도 검사할 수 있으므로, PASS만으로 새로 복제한 저장소에서의 재현이나 원격 반영을 주장하지 않는다. PDF 페이지·발표자 노트·대본의 내용 및 렌더 이미지의 실제 출처는 발표자료 검증 영수증과 별도 시각 검토로 확인한다. 이 검사는 기록된 파일 해시와 순서를 대조하며 그 내용의 의미까지 판정하지 않는다.

후보(`candidate`), 빠진 해시, 서로 다른 사본, 잘못된 슬라이드 수, 수정 후 오래된 해시, 정책 불일치는 실패한다. 검사 영수증은 산출물 밖에 저장한다. 과거 앱의 build-info에 새 기준표의 해시가 들어 있어야 한다는 순환 조건을 만들지 않는다.

테스트:

```powershell
python -m unittest discover -s scripts/release -p test_product_release.py -v
```

## 공개 반영 순서

1. 제품·자료를 수정하고 각각 검증한다. 개인 제출 문서와 작업 폴더는 공개 대상에서 제외한다.
2. 새 앱이 필요하면 새 버전 설치 파일을 먼저 검증하고 공개 릴리스로 보존한다. 웹의 기능 설명이 그 앱에서 지원되는지 확인한다.
3. 공식 발표 파일을 확정하고 해시·39장 순서·발표자 노트·대본·PDF를 검증한다. 원본 PPTX는 25 MiB를 넘으므로 Worker 정적 자산에 그대로 넣지 않는다. 대용량 다운로드는 실제 공개가 확인된 경로만 사용한다.
4. 기준표와 두 사본, Website 39장 미리보기를 갱신하고 위 통합 검사를 통과시킨다.
5. 저장소별 공개 보안 검사를 통과시킨 뒤 게시·Website 배포를 수행한다. 실제 배포 후 다운로드 버전·발표자료 순서와 링크를 다시 확인해야 공개 반영 완료다.

Git push와 Website 배포는 여러 원격 작업이므로 원자적으로 함께 바뀌지 않는다. 이전 배포를 유지한 채 새 후보를 검증하고, 모든 자산이 준비된 뒤 Web을 마지막에 전환한다. 작업트리 검증 PASS를 원격 반영 완료로 표시하지 않는다.
