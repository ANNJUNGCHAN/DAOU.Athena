# LAYA 전체 조회 카탈로그 선택 실험

2026-10-01 기준의 옵트인 구현이다. 기본값은 `ATHENA_LAYA_ENABLED=false`이며,
파인튜닝이나 모델 가중치 변경을 하지 않는다. 실제 주문은 개발 범위에 포함하지 않는다.

## 선택 범위와 입력

`POST /api/v1/laya/select-operation`은 `text`와 `catalog_version`만 받는다.
호출자가 고른 후보 목록, 선택 지시문, 스키마는 받지 않는다. 백엔드의
`OperationCatalog.visible_for(QUERY)`에서 `generic_callable`인 모든 기능을 읽는다.
현재 266개이며 일반 조회 264개와 읽기 전용 조건검색 2개(`ka10171`, `ka10172`)다.
115개 detail projection을 각각 선택지로 포함한다. 분할된 22개 base는 실행 가능한
선택지가 아니므로 detail로만 표현한다. 주문 12개, 나머지 websocket 21개, OAuth 2개는
조회 선택 범위에 포함하지 않는다. `/api/v1/catalog`의 전체 301개와 혼동하지 않는다.

선택지 문구는 카탈로그의 한국어 detail 이름 또는 기능명, 상위 기능명, 하위 분류,
출력 형태를 조합한다. 모델에는 `base:...` 같은 operation ID를 설명으로 넣지 않는다.
사용자 문장은 `state.text`에 전달하고, 각 질문의 `criteria`에는 `c0`, `c1` 등의
임시 키와 선택지 설명을 넣는다. 서버가 임시 키를 canonical operation ID로 다시 매핑한다.
266개 기능의 선택용 설명은 모두 첫 단계 질문에 포함한다. 함수별 전체 입력값
스키마, 과거 대화, few-shot 예시는 LAYA에 주입하지 않는다. 선택된 기능의 전체
입력값 스키마는 이후 CLI 인자 추출 단계에 전달한다. 따라서 줄이는 것은 선택
가능한 기능의 범위가 아니라, 선택 이후 CLI가 읽는 여러 후보의 명세다.

## 전체 범위를 평가하는 방법

1. 카탈로그를 고정된 ID 순서로 정렬한 기존 순서에서 9개 이하씩 나눈다. 모든 기능을
   첫 단계 질문에 포함한다. 질문은 한 HTTP 요청에 최대 8개씩 묶는다.
2. 중간 질문은 그 묶음에서 가장 관련 있는 기능 하나를 선택한다. 최종 실행 판단이
   아니므로 낮은 confidence만으로 후보를 삭제하지 않는다. 한 개만 남은 묶음도
   `None`과 함께 실제로 평가한 뒤 다음 단계로 넘긴다.
3. 묶음별 승자를 다시 9개 이하씩 비교한다. 서로 다른 질문의 softmax 점수를
   직접 비교하거나 전체 카탈로그 점수처럼 합치지 않는다.
4. 마지막 9개 이하의 후보에는 `None`을 추가한다. `answer_confidence >= 0.8`과
   1·2위 차이 `>= 0.15`의 기존 수락 기준을 적용한다.
5. 카탈로그를 역순으로 놓고 같은 전체 과정을 다시 수행한다. 두 최종 응답이 모두
   기준을 만족하고 같은 operation ID를 선택했을 때만 후보를 반환한다.

266개에서는 한 방향에 30 + 4 + 1 = 35개 질문, 6개 HTTP 요청이며 두 방향은
70개 질문, 12개 HTTP 요청이다. `max_len=2048`, `head_max_len=512`를 사용한다.
원문 전체와 선택지의 실제 토큰 길이를 별도 검사해야 하며, 글자 수만으로 입력 보존을
판정하지 않는다. 알고리즘은 모든 기능을 평가하되, 중간 비교에서 패한 후보가 이후에
다시 살아나는 구조는 아니다.

## 계약과 실패 처리

수락 응답의 `candidate`는 모델이 작성하지 않는다. `SelectorService.describe`로 읽은
필수·선택 입력값의 정확한 계약을 서버에서 구성한다. CLI는 선택된 기능의 입력값을
추출하고 기존 selector가 원래 사용자 질문과 함께 검증한다. 기존 3개 후보 preflight는
실패 시 CLI 폴백용으로 유지한다. 일반 코드가 즉시 결정하는 경로는 변경하지 않는다.

`considered_count`는 전체 대상 수, `evaluated_count`는 완전히 검증된 모델 응답에서
실제로 평가된 고유 기능 수, `question_count`는 모델에 보낸 질문 수다. 성공 시
`considered_count == evaluated_count == 266`이어야 한다. 일부 묶음만 성공한 경우는
선택 결과를 반환하지 않는다. 카탈로그 버전 불일치는 모델을 호출하기 전에 폴백한다.

한 전체 판단의 제한 시간은 `ATHENA_LAYA_CATALOG_TIMEOUT_SECONDS` 기본 5초이며
0.1–15초 범위다. 각 HTTP 요청에는 기존 `ATHENA_LAYA_TIMEOUT_SECONDS` 기본 1.2초도
적용한다. 취소는 상위 호출로 전파하고 잠금을 해제한다. 시간 초과, 연결 실패, 잘못된
모델 ID, 누락·추가된 질문/확률 키, 중복 JSON 키, 비정상 확률은 결과를 폐기하고 기존
CLI 경로로 돌아가게 한다. 전체 판단 중에는 같은 서비스의 중복 판단을 시작하지 않는다.

## 연구 근거와 적용 한계

[Setwise prompting 연구](https://arxiv.org/html/2310.09497v2)는 제한된 수의 항목을
묶어 비교하는 검색 재정렬 접근의 근거로 참고했다. 이 구현은 모든 조회 기능을 작은
묶음으로 비교하는 데 그 아이디어를 사용한다. 논문의 검색 데이터·모델에서 얻은 결과가
LAYA의 한국어 금융 API 선택 성능을 보증하는 것은 아니다.

[Pairwise ranking prompting 연구](https://aclanthology.org/2024.findings-naacl.97/)는
작은 비교 문제로 순위를 구성하는 접근의 참고 자료다. 현재 구현은 모든 쌍을 비교하는
방식이 아닌 setwise 토너먼트다. 순서 편향을 줄이기 위해 전체 카탈로그 역순 확인을
추가했지만, 두 순서의 일치가 정확성이나 모든 가능한 순서에 대한 불변성을 보증하지 않는다.

[LAYA multilingual 모델 카드](https://huggingface.co/convaiinnovations/laya-multilingual)는
선택 후보에 대한 분류 응답과 확률의 의미를 확인하는 공식 자료다. 실제 실행에서는
설치된 모델·SDK·로컬 HTTP 래퍼의 제한도 별도로 확인한다.
[Guo 외의 calibration 연구](https://proceedings.mlr.press/v70/guo17a.html)는 신경망의
confidence를 실제 정답 확률로 그대로 읽으면 안 된다는 근거다. 여기서 0.8은 실험적인
수락 기준이며 80% 정답률이라는 뜻이 아니다. 별도 보정 모델도 학습하지 않았다.

모의 응답을 사용한 자동 테스트는 전체 범위 포함, 입력 계약, 중단·폴백과 응답 검증을
확인한다. 실제 의미 정확도, CLI 전체 입력 토큰 감소, 사용자에게 보이는 총 응답 시간은
실제 모델 비교에서 따로 측정한다. 현재 구현만으로 그 개선을 주장하지 않는다.
