# 카드 UI 전체 완료 목표 실행 계획

작성일: 2026-10-04
실행 브랜치: `codex/card-ui-resume-20261003`
시작 기준: `7e69c99`
상태: **ACTIVE — 전체 완료 전 종료하지 않음**

## 1. 최종 결과와 완료 조건

목표는 Paper의 편집 가능한 상태 101개를 보존·개선하고, 그중 개발 범위인 실제 Athena 앱 상태 94개를 현재 설치 소스로 모두 검증하는 것이다. 실거래·실제 주문 실행에 해당하는 참고 상태 7개는 실행 대상에서 제외하되 Paper 참조 도면으로 유지한다.

아래 조건을 모두 만족할 때만 목표를 완료로 판정한다.

1. Paper 파일에서 편집 가능한 상태가 정확히 101개이며, 기존 상태가 누락·평면화·중복되지 않는다.
2. 101개 각각에 `paper_reference`, 의도, 상태 이름, 개선 여부가 기록된다. Paper 도면 ID와 앱의 실제 상태 ID는 근거 없이 동일한 ID로 간주하지 않는다.
3. 개발 범위 94개 각각에 실제 앱에서 확인한 runtime template ID 또는 재현 가능하고 상태를 고유하게 식별하는 route assertion이 있다. runtime ID를 UI에서 확인할 수 없으면 null을 유지하며 Paper·질문지의 디자인 참조 ID를 복사하지 않는다.
4. 94개 모두 같은 카드 인스턴스에서 `2560×1392 최대 → 1411×1166 축소 → 2560×1392 재최대` 순서를 실제 달성한 창 크기와 함께 통과한다. 다른 크기나 공개 fixture 결과로 대체하지 않는다.
5. 각 상태의 상단·하단·마지막 행·마지막 열, 해당되는 탭·정렬·펼침·스크롤·복귀 동작을 확인한다. 일부 영역 통과를 전체 카드 통과로 올리지 않는다.
6. 빈 상태, 오류, 부분 데이터, 시간 초과, 긴 값, 0·음수 값처럼 해당 카드가 지원하는 상태를 실제 경로에서 확인한다. 없는 금융 값은 만들거나 다른 출처 값으로 대체하지 않는다.
7. 발견된 결함은 수정 후 영향받은 상태와 공유 렌더러를 재검증하고, 전체 단위 검사·독립 검토·보안 게이트를 통과한다.
8. 정상 Git 훅을 거쳐 UI 브랜치에 push하고 원격 HEAD 일치와 깨끗한 작업 트리를 확인한다. `main` 병합과 LAYA 브랜치 변경은 목표에 포함하지 않는다.

엄격한 현재 완료 수는 **Paper 0/101 재확인, 실제 앱 0/94 전체 사이클 완료**로 시작한다. 이전의 800/800 단위 검사, 합성 렌더러 통과, 월봉 1개 제한 크기 관측은 유효한 기반 증거지만 위 완료 수에는 포함하지 않는다.

## 2. 범위와 증거 층위

| 층위 | 목적 | 완료에 사용할 수 있는 범위 |
| --- | --- | --- |
| Paper | 101개 편집 도면 보존, 시각 설계 및 상태 의도 확인 | Paper 보존·디자인 판정만 가능 |
| 소스/fixture | 렌더러 계약, 회귀, 경계값을 빠르게 검사 | 수정의 안전성과 재현성 증명; 실제 앱 94개 완료 대체 불가 |
| 실제 앱 | 라우팅, 실제 렌더러, 동일 카드 리사이즈·상호작용 확인 | 94개 완료 판정의 필수 근거 |
| 독립 검토 | 증거 귀속, 누락, 과장, 회귀 여부 확인 | 최종 승인 필수; 작성자가 스스로 승인하지 않음 |

금융 화면 캡처, 계좌 수치, 사용자 프로필, 인증 정보, 대화 DB는 Git과 Paper에 올리지 않는다. 실제 화면은 ignored 로컬 증거에만 두고 공개 기록에는 상태·창 크기·소스 해시·판정·비식별 캡처 해시만 남긴다.

## 3. 실행 순서

### M0. 실행 기준 고정과 장비 준비

- 별도 worktree와 UI 브랜치가 `7e69c99` 및 origin과 일치하는지 확인한다. 기존 `main`의 32개 수정·4개 미추적 파일은 건드리지 않는다.
- 앱 의존성, backend 환경, 현재 제품 파일 해시, 단위 검사 800/800, 보안 게이트 기준을 다시 기록한다.
- Computer Use가 실제 Athena 창을 안정적으로 열거·관측·입력할 수 있는지 확인한다. 입력 소유자는 한 번에 한 명으로 제한한다.
- 물리 디스플레이 크기만으로 목표 logical window가 가능하다고 판정하지 않는다. 실제 디스플레이·배율 조합 또는 BrowserWindow 제어 중 하나를 선택해 `2560×1392`, `1411×1166`의 전체 창 raster와 입력 좌표를 보장하는 경로를 증명한다.
- 모든 관측에 `window_outer_size`와 `renderer_viewport_size`를 함께 기록한다. 요구사항의 `2560×1392 → 1411×1166 → 2560×1392`는 `window_outer_size` 기준으로 고정하고, viewport는 렌더러 영역 회귀 판단에 사용한다. 전체 outer 창의 우측 끝과 하단이 한 캡처 또는 검증 가능한 연속 캡처에 포함되지 않으면 PASS가 아니다.
- 현재 물리 디스플레이 후보가 2560×1440/2880×1800이어도, 목표 logical outer 크기를 실제 관측하기 전에는 환경 통과로 세지 않는다. 화면 밖으로 잘린 창, OS 배율 때문에 일부만 보이는 창, API가 보고한 크기만 있고 전체 raster가 없는 창도 인정하지 않는다.
- 브라우저의 Paper 로그아웃을 전체 Paper 접근 실패로 일반화하지 않는다. 현재 열려 있는 native Paper 앱을 우선 관측해 대상 ATHENA 파일 ID, 편집 권한, 페이지/도면 목록을 읽을 수 있는지 확인한다. 실제로 읽고 수정할 수 있는 단일 표면을 이번 실행의 Paper 작업 표면으로 고정한다.

통과 기준: 소스 기준과 실행 환경 receipt가 있고, 실제 앱 창·Paper 파일 모두 읽을 수 있으며 목표 outer 크기 두 개와 전체 raster 관측을 실제로 달성한다. 달성 불가 시 크기를 낮추지 않고 요구사항 소유자만 변경할 수 있는 차단 조건으로 남긴다.

### M1. 101개 기준표와 Paper 보존선 확정

- `backend/ref/card-ui-questionnaire.json`의 101개 항목을 기준표로 사용한다: `in_scope` 94개, `reference_only` 7개.
- 실제 앱 작업 묶음은 account 14, instrument 31, orderbook 8, explorer 26, flow 15로 구성한다. reference-only는 order 6개와 orderbook 1개이며 실행 묶음에서 제외한다. 항목별 `scope` 값을 최종 기준으로 삼는다.
- 각 항목에 Paper 참조, 앱 route/source, 최소 seed 또는 UI navigation, 선행조건, 기대 카드 종류, 기능 체크 목록을 연결한다.
- 현재 첫 UI 이동에 복수 후보가 있는 21개 항목은 각각 클릭 후 카드 종류, 선택된 탭/정렬 값, operation 결과 형태 또는 제품이 노출하는 runtime metadata 중 하나 이상의 고유 assertion을 정의한다. assertion 없이 후보 중 하나를 임의 선택하지 않는다.
- `15J9-2`는 `prompt: null`, `ui_steps: []` 상태를 먼저 해소한다. 별도 최소 입력을 만들거나 검증된 부모 상태에서 시작하는 UI 이동과 도착 assertion을 확보한다. 확보 전에는 `NOT_RUN`이고 M1을 통과하지 않는다.
- 31개 additional flow는 별도 실행 보조 목록으로 관리한다. 실행 범위는 30개이며 `protected-action` 1개는 reference-only다. validator가 제외 흐름을 native 실행 큐에 넣지 못하게 한다. 이 흐름 수를 94개 template 수와 합산하지 않는다.
- Paper 작업 표면에서 편집 가능한 상태 101개를 직접 세고 각 참조를 기준표에 연결한다. 수정 전 101개 항목의 ID·이름·부모 구조·편집 가능 여부 snapshot을 저장한다. 이름이 비슷해도 시각 도면과 실제 앱 상태를 자동으로 같은 항목으로 간주하지 않는다.
- 원본 101개를 보존한 상태에서 개선본을 작성한다. 구조·상태 의미를 바꾸는 디자인 변경은 앱 계약과 함께 검토한다.

통과 기준: 101/101 Paper 참조가 있고, 94/94 모두 실제 실행 가능한 route와 상태 고유 assertion을 가지며, reference-only 7개와 excluded additional flow 1개가 실행 큐에서 분리되어 있다. 미해결 route, 누락·중복·ID 추정은 0건이다.

### M2. 실제 앱 검증 장부와 자동 판정 규칙 구축

94개 행의 단일 장부를 만들고 각 행에 다음 필드를 기록한다.

`item_id`, `expected_design_reference_id`, `paper_reference`, `scope`, `expected_card_kind`, `seed_or_route`, `route_source`, `route_identity_assertions`, `observed_runtime_template_id`, `runtime_source_hashes`, `card_instance_marker`, `call_status`, `window_outer_sizes`, `renderer_viewport_sizes`, `full_raster_evidence`, `max_checks`, `narrow_checks`, `remax_checks`, `interaction_checks`, `privacy_class`, `evidence_refs`, `bug_ids`, `review_status`, `freshness_status`, `final_status`.

`final_status`는 `PASS`, `FAIL`, `NOT_RUN`, `BLOCKED_EXTERNAL`만 사용하고, `freshness_status`는 `CURRENT`, `REVALIDATE`만 사용한다. 현재 질문지의 94개 `observed_template_id`가 모두 null이라는 시작 receipt를 고정한다. validator는 `expected_design_reference_id`나 Paper ID가 `observed_runtime_template_id`로 복사된 경우를 거절한다. runtime ID가 null이면 `route_identity_assertions`가 다른 상태와 구분되는 경우에만 route 근거를 인정한다.

사람이 `final_status: PASS`를 직접 입력하지 않는다. validator가 목표 outer 크기 3단계, 각 단계 viewport와 전체 raster, 동일 `card_instance_marker`, route 고유성, 필수 영역·상호작용, 최종 source hash, `freshness_status: CURRENT`가 모두 채워진 경우에만 PASS를 계산한다. `scoped_pass`와 합성 fixture 통과는 참고 증거이며 최종 PASS가 아니다. 카드 미도착, 크기 불일치, 같은 카드 미확인, 하단 미관측, 고유 route 부재 중 하나라도 있으면 완료되지 않는다.

통과 기준: 94개 행이 생성되고 필수 필드 누락을 검사하는 검증기가 있으며, 완료 수는 장부에서 기계적으로 계산된다.

### M3. 카드 종류별 실제 앱 실행과 결함 수집

실행 순서는 공통 렌더러 영향이 큰 묶음부터 진행한다.

1. instrument 31: 시세·기업정보·기간/월봉/주봉 차트·단위·날짜축·거래량·전환·복귀
2. orderbook 8: 호가 열·매수/매도 구분·마지막 열·가로 이동·빈/부분 상태
3. account 14: 읽기 전용 잔고·자산·주문/체결 조회, 부분 미제공 안내, 마지막 행·열
4. explorer 26: 목록·랭킹·뉴스·공시·검색, 정렬·탭·펼침·긴 값·빈 상태
5. flow 15: 복합 이동·대화 복귀·카드 교체·오류 및 시간 초과 복구

각 항목은 한 번 호출한 같은 카드에서 다음을 순서대로 수행한다.

1. 최대 2560×1392에서 상단·핵심 값·출처·단위·기본 상호작용 확인
2. 1411×1166으로 축소한 뒤 상단, 하단, 마지막 행·열, overflow와 해당 탭·정렬·펼침 확인
3. 같은 카드임을 확인한 채 2560×1392로 재최대화하고 위치·축·선택·탭·데이터가 정상 복원되는지 확인
4. actual size, 소스 해시, route 근거, 비식별 캡처 해시와 판정을 장부에 즉시 기록

12개 최소 seed와 실행 범위인 추가 흐름 30개를 재사용해 호출 수를 줄이되, 하나의 호출이 여러 항목을 보여 줄 경우에도 각 항목의 독립 체크를 남긴다. `protected-action` 제외 흐름은 호출하지 않는다. 실제 주문 버튼은 누르지 않고 주문 실행 가능 여부도 시험하지 않는다. 주문·체결 내역 조회는 읽기 전용으로만 확인한다.

통과 기준: 해당 묶음의 모든 행이 PASS이거나 결함 장부로 이동한다. 외부 데이터가 없어 확인할 수 없는 상태는 PASS로 만들지 않는다.

### M4. 결함 수정 루프

결함마다 `bug_id`, 재현 항목, 최초 실패 단계, 영향 카드 종류, 소유 파일, 기대 동작, 회귀 검사, 실제 앱 재검증 범위를 정한다.

- 먼저 실패를 재현하는 최소 회귀 검사를 추가하거나 기존 공개 소비자 fixture로 고정한다.
- 공유 CSS/렌더러 변경은 selector 누출과 비대상 카드 기하를 검사한다. 단일 카드 결함은 해당 route에만 최소 수정한다.
- 수정 후 대상 행 전체 사이클과 같은 공유 렌더러를 쓰는 이전 PASS 행을 다시 실행한다.
- 수정으로 제품 소스 해시가 바뀌면 그 소스의 영향을 받는 모든 기존 실제 앱 행의 `freshness_status`를 `REVALIDATE`로 바꾼다. 이때 validator는 기존 `final_status`와 무관하게 완료 수에서 제외한다. 영향 범위가 증명되지 않으면 94개 전체를 재검증한다.
- 회귀가 생기면 마지막 검증된 커밋에서 변경 파일만 역방향 패치로 되돌리고 장부를 복원한다. `reset --hard`, force-push, 훅 우회는 사용하지 않는다.

통과 기준: 열린 bug 0건, `FAIL/NOT_RUN/BLOCKED_EXTERNAL` 0건, `freshness_status: REVALIDATE` 0건, 영향받은 실제 앱 행 전부 재통과.

### M5. Paper 개선본과 앱 결과의 대조

- 실제 앱에서 확정한 문제와 수정 결과를 Paper 개선본에 반영하되 원본 101개는 보존한다.
- 각 Paper 디자인 참조가 실제 앱의 어느 route와 대응하는지 다시 확인한다. 디자인 참조 ID와 runtime template ID는 별도 열에 유지한다.
- Paper만 좋아 보이고 앱에 반영되지 않은 차이, 앱만 변경되고 Paper에 반영되지 않은 차이를 각각 0건으로 만든다.
- 7개 reference-only 상태는 실거래 실행 없이 시각 참조와 범위 표기만 확인한다.

## 4. 장애 처리와 멈춤 규칙

목표는 완료될 때까지 ACTIVE를 유지한다. 다음 상황은 실패를 숨기지 않고 복구 작업으로 전환한다.

- Paper 로그인이 연결된 세션에 보이지 않음: 다른 프로필을 추측하지 않고 연결 세션을 다시 확인한다. 인증 정보는 읽거나 복사하지 않는다.
- Computer Use 창 열거/입력 시간 초과: 세션을 재초기화하고 현재 창을 다시 획득한다. 과거 handle·PID·screenshotId를 재사용하지 않는다.
- 목표 크기 미달: 현재 모니터에서의 대체 크기를 증거로 보존할 수는 있지만 완료로 세지 않는다. 목표 크기를 제공하는 검증 환경으로 이동한다.
- 카드 미도착/API 실패: 동일 요청을 무한 반복하지 않는다. 호출 로그와 UI 상태를 분리해 기록하고, 제품 결함인지 외부 서비스 장애인지 최소 진단한다. 외부 장애이면 `BLOCKED_EXTERNAL`로 남겨 재시도 큐에 넣는다.
- 실제 금융 데이터 부재: 값을 합성하거나 다른 API로 몰래 대체하지 않는다. 해당 상태는 NOT_RUN/BLOCKED_EXTERNAL로 유지한다.
- 새 결함 발견: 현재 묶음의 안전한 관측을 끝낸 뒤 M4로 이동하고, 영향받는 PASS를 재검증 대상으로 되돌린다.

사용자 입력이 반드시 필요한 인증·외부 권한 장애가 아닌 한 계획·수정·검증을 계속한다. 외부 장애가 있어도 독립적인 다른 카드 묶음과 소스 검증을 병행하며, 모든 실행 가능 작업이 소진된 경우에만 정확한 차단 조건과 필요한 사용자 조치 한 가지를 보고한다.
